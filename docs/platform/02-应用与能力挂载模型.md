## 1. 为什么需要本层

能力地图解决「平台有哪些能力」；业务方感知的是「一个可用的应用」。

主流平台（Dify / 云 AI Studio 等）普遍存在：

```text
Tenant / Workspace
    └── Application（Bot / App）
            ├── 挂载能力：RAG / Chat / Agent / Generation / DocIntel
            ├── 配置：模型、知识库、工具、Prompt、工作流
            └── 入口：Web 对话 / API / 批任务
```

没有这一层，容易把「再建一个聊天页」和「再建一个能力域」混为一谈。

## 2. 核心对象模型

### 2.1 层级（目标模型；MVP 可简化）

| 对象 | 含义 | MVP 简化 |
| :--- | :--- | :--- |
| **tenant** | 租户/公司 | 可省略，单租户 |
| **workspace** | 团队空间 | 可省略，或 = 一个部门 |
| **app** | 面向用户的应用实例 | **首期必有**（哪怕只有一张配置表） |
| **capability binding** | App 挂载了哪些能力与资源 | JSON 配置亦可 |
| **workflow**（可选） | 节点编排（检索→LLM→分支→工具） | P2+；首期可用「固定链路」代替 |

### 2.2 App 最小字段（建议）

| 字段 | 说明 |
| :--- | :--- |
| id / name / description | 应用标识 |
| app_type | `rag_chat` / `assistant` / `agent` / `generation` / `doc_intel` / `custom` |
| status | draft / published / disabled |
| model_profile_id | 引用网关侧模型配置（见 03） |
| bindings_json | 挂载资源：kb_ids、tool_ids、prompt_id、workflow_id 等 |
| entrypoints | `web` / `api` / `batch` |
| owner / workspace_id | 归属 |

### 2.3 能力挂载示例

**制度问答 App（首期）**

```text
app_type: rag_chat
bindings:
  kb_ids: [1]
  prompt_id: "rag_default"
  retrieve: { top_k: 4, hybrid: false }
  model_profile: "default_chat"
entrypoints: [web, api]
```

**办公助手 App（P2）**

```text
app_type: assistant
bindings:
  system_prompt_id: "office_assistant"
  model_profile: "default_chat"
  tools: []          # 暂无
entrypoints: [web]
```

**审批辅助 Agent（P3）**

```text
app_type: agent
bindings:
  tools: ["kb_search", "order_query"]
  hitl_policies: ["order_query.write"]
  model_profile: "agent_chat"
entrypoints: [web, api]
```

## 3. Workflow（可选，与固定链路关系）

| 模式 | 适用 | 说明 |
| :--- | :--- | :--- |
| **固定链路** | RAG MVP | 代码内写死：检索 → Prompt → LLM → 引用 |
| **可配置 Workflow** | 多步/多分支 | 节点：Input / Retrieve / LLM / Tool / Branch / HITL / Output |

约定：

- 首期 RAG **不强制**上工作流引擎  
- 一旦出现「同一知识库、不同问答策略要运营可配」，再引入 Workflow，避免过早造编排器  
- Agent 域的多步循环可先做「代码状态机」，再演进到可视化 Workflow

## 4. 统一工作台（前端信息架构）

最小页面清单（平台级）：

| 页面 | 作用 | 首期 |
| :--- | :--- | :---: |
| 应用列表 | 创建/发布/停用 App | ✅ |
| 应用配置 | 模型、知识库、Prompt、工具挂载 | ✅（RAG 子集） |
| 对话台 | 按 App 进入会话 | ✅ |
| 知识库管理 | 文档/任务（RAG 域） | ✅ |
| 任务中心 | 入库/批生成进度 | ✅ |
| 工具与安全 | 工具注册、HITL 策略 | P3 |
| 观测与反馈 | Trace、点赞点踩、评测 | P2 起 |

原则：**一个工作台入口 + 按 App 挂载功能页**，而不是每个能力域各做一个互不相通的门户。

## 5. API 约定（粘合层）

建议增加（可与域 API 并存）：

| 方法 | 路径 | 说明 |
| :--- | :--- | :--- |
| GET/POST | `/api/v1/apps` | 应用 CRUD |
| GET | `/api/v1/apps/{id}` | 含 bindings |
| POST | `/api/v1/apps/{id}/chat` | **统一对话入口**（内部按 app_type 路由到 rag/assistant/agent） |
| GET | `/api/v1/apps/{id}/config` | 前端拉配置 |

域内 API（`/api/v1/rag/...`）仍保留，供管理与调试；**对终端用户优先走 App 入口**，便于后续换链路不改前端。
