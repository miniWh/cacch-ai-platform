## 1. 什么是提示词模板

**提示词模板**（Prompt Template）是一种结构化的提示词书写范式，它将一段提示词拆分为"固定部分"与"可变部分"：

- **固定部分**：角色设定、任务指令、约束规则、输出格式等不变的指令；
- **可变部分**：使用占位符（如 `{{topic}}`、`{input}`）表示每次调用时动态填充的内容。

用一句话概括：**模板 = 稳定的指令框架 + 可变的业务参数**。

```text
你是{{role}}。请完成以下任务：{{task}}。
要求：{{constraints}}。
输出格式：{{output_format}}。
```

在实际的 AI 应用（如 RAG 问答、Agent 工作流、内容生成系统）中，模板通常由代码动态渲染后发送给大模型，例如 Python 中的 `str.format()` 或 `f-string`、Java 中的 `String.format()`、前端模板引擎等。

## 2. 为什么要使用模板

| 价值 | 说明 |
|------|------|
| **稳定性** | 固定指令结构，避免每次书写时遗漏关键要素，保证输出质量一致 |
| **可复用** | 同一模板可套用于大量相似任务，只需替换变量 |
| **可维护** | 指令逻辑集中在模板中，修改一处即可全局生效 |
| **可测试** | 便于对模板进行批量评估与回归测试（如 A/B 对比不同模板的生成效果） |
| **安全可控** | 将用户输入隔离在占位符中，配合转义/过滤可降低提示注入风险 |

## 3. 通用模板结构

大多数高质量提示词模板都包含以下 6 个核心模块，可按需取舍：

```
┌─────────────────────────────────────────┐
│ 1. 角色（Role）     你是谁，扮演什么角色     │
│ 2. 任务（Task）     要完成什么，目标是什么     │
│ 3. 上下文（Context）背景信息、输入材料         │
│ 4. 约束（Constraints）不能做什么、边界条件    │
│ 5. 输出格式（Format）结构、长度、风格要求      │
│ 6. 示例（Example）   Few-shot 样例示范       │
└─────────────────────────────────────────┘
```

**记忆口诀：RTFC-FE（Role, Task, Context, Constraints, Format, Example）**

各模块编写要点：

| 模块 | 要点 |
|------|------|
| 角色 Role | 明确专业身份，如"你是资深 Java 架构师"；可附带语气风格 |
| 任务 Task | 使用祈使句，动词开头，如"总结""翻译""生成 SQL" |
| 上下文 Context | 提供必要背景，让模型有依据；信息宁精勿滥 |
| 约束 Constraints | 负面约束（禁止编造、禁止超出范围）与正面约束（必须基于给定材料） |
| 输出格式 Format | 指定 Markdown/JSON/表格等，并给出字段结构 |
| 示例 Example | 1~3 个输入输出对，示范期望的行为模式 |

## 4. 经典模板框架

### 4.1 CRISPE

由 Matt Nigh 提出的结构化提示框架，共 5 个步骤：

| 字母 | 含义 | 说明 |
|------|------|------|
| C | Capacity / Role | 设定角色与能力 |
| R | Insight | 提供背景、意图与上下文 |
| S | Statement | 陈述任务与目标 |
| P | Personality | 定义风格与个性 |
| E | Experiment | 要求给出多个方案并说明取舍 |

**模板骨架：**

```text
扮演{{role}}。
背景：{{background}}。
任务：{{task}}。
风格：{{style}}。
请给出{{n}}种方案，并比较各自的优缺点，最后推荐一个。
```

### 4.2 CO-STAR

新加坡政府科技局（GovTech）提出的实用框架，尤其适合业务场景：

| 字母 | 含义 | 说明 |
|------|------|------|
| C | Context | 提供背景与业务场景 |
| O | Objective | 明确目标与期望结果 |
| S | Style | 指定写作风格 |
| T | Tone | 指定语气（正式/亲切/紧迫） |
| A | Audience | 明确受众 |
| R | Response | 规定输出格式 |

**模板骨架：**

```text
# CONTEXT
{{背景信息}}

# OBJECTIVE
{{要达成的目标}}

# STYLE
{{风格要求}}

# TONE
{{语气要求}}

# AUDIENCE
{{目标受众}}

# RESPONSE
{{输出格式要求}}
```

### 4.3 RTF 三段式

最简洁的通用模板，适合日常快速使用：

```text
Role（角色）：你是{{role}}
Task（任务）：请{{task}}
Format（格式）：请以{{format}}输出
```

### 4.4 角色模板

通过角色设定提升输出的专业性，常与其他框架组合使用：

```text
你是一位资深的{{profession}}，拥有{{years}}年{{domain}}领域经验。
现在请从专业角度出发，{{task}}。
在回答时请注意：{{constraints}}。
```

### 4.5 Few-Shot 示例模板

通过 1~3 组"输入→期望输出"样例，示范模型的响应模式，适用于分类、抽取、改写等任务：

```text
请根据以下示例完成同样的任务。

示例 1：
输入：{{example_input_1}}
输出：{{example_output_1}}

示例 2：
输入：{{example_input_2}}
输出：{{example_output_2}}

现在轮到你了：
输入：{{real_input}}
输出：
```

### 4.6 思维链模板

引导模型逐步推理，显著提升复杂任务的正确率：

```text
请逐步思考并回答以下问题：
问题：{{question}}

步骤要求：
1. 先列出已知条件；
2. 分析问题与已知条件的关系；
3. 分步推导得出结论；
4. 最后用一句话总结答案。
```

## 5. 模板变量与占位符

模板中的可变部分通过**占位符**标识，常见写法：

| 写法 | 示例 | 说明 |
|------|------|------|
| 双花括号 | `{{topic}}` | 最通用，兼容多语言与模板引擎 |
| 单花括号 | `{input}` | Java `String.format`、Python `format` 常用 |
| 尖括号 | `<INPUT>` | 常见于 Anthropic 等官方文档示例 |
| 混合风格 | `${{variable}}` | GitHub Actions 等工具链写法 |

**占位符命名规范：**

- 使用语义化、小写、下划线分隔：`user_name`、`query_text`，而非 `var1`；
- 占位符即"契约"，模板文档中应附带变量说明表（名称、类型、必填、示例）；
- 用户输入放入占位符时，注意长度截断与特殊字符转义，防止模板被破坏或提示注入。

## 6. 实战示例：中文场景模板

### 示例 A：内容总结模板

```text
你是一位资深编辑，擅长提炼信息核心。

请阅读以下材料，输出一份 200 字以内的中文摘要。

【材料】
{{document}}

【要求】
- 保留关键数据与结论；
- 不添加材料之外的信息；
- 使用 Markdown 段落格式，不要使用列表。
```

### 示例 B：SQL 生成模板

```text
你是精通 PostgreSQL 的数据库专家。

【表结构】
{{schema}}

【业务需求】
{{requirement}}

请生成一条满足需求的 SQL 查询语句，并：
- 只输出 SQL，不要额外解释；
- 使用合适的索引列过滤；
- 如需多表关联，请说明关联字段。
```

### 示例 C：RAG 问答模板（生产常用）

```text
你是企业知识库助手。请仅基于以下资料回答用户问题。
如果资料中没有相关信息，请直接回答"资料库中未找到相关内容"，不要编造。

【资料】
{{retrieved_context}}

【问题】
{{question}}

【要求】
回答时标注信息来源片段，控制在 150 字以内。
```

### 示例 D：代码审查模板

```text
你是一位经验丰富的 {{language}} 开发工程师。

请审查以下代码，输出审查意见：
1. 严重问题（Bug / 安全隐患）；
2. 潜在风险（性能 / 并发 / 边界条件）；
3. 可读性建议。

【代码】
{{code}}
```

## 7. 编写模板的最佳实践

1. **任务指令放在提示词开头**：多数模型对开头与结尾指令更敏感，角色与任务优先置顶；
2. **明确输出格式**：规定结构、长度、语言，减少解析成本（如直接要求输出 JSON）；
3. **负面约束要具体**："不要编造"优于"请准确"，"禁止超出给定资料"优于"请谨慎";
4. **适当使用示例**：Few-Shot 示例比长篇规则更有效，但示例要典型、数量适度（1~3 个）；
5. **分隔符清晰**：用 `【】`、`---`、`#` 等明确区分"指令"与"输入数据"；
6. **变量先校验**：渲染前检查必填变量是否存在、长度是否超限；
7. **模板版本化**：将模板纳入 Git 管理，改动后对历史用例做回归对比；
8. **温度等参数协同**：抽取类任务调低 temperature（如 0~0.3），创意类任务可适当调高。

## 8. 常见误区

| 误区 | 后果 | 建议 |
|------|------|------|
| 模板冗长、堆砌指令 | 模型抓不住重点，输出发散 | 精简指令，突出核心要求 |
| 占位符命名随意 | 难以维护与测试 | 语义化命名 + 变量文档 |
| 不加分隔符，指令与数据混在一起 | 模型混淆任务与内容 | 用固定标记分隔 |
| 约束全是正面描述 | 边界不清 | 明确写出禁止项 |
| 示例过多 | 消耗上下文、拖慢响应 | 控制在 1~3 个 |
| 模板从不迭代 | 效果长期停留在初版 | 建立评估集，持续优化 |
